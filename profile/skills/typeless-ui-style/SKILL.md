# Typeless UI Style

把 Typeless 的视觉原则转成适合目标产品的设计决策，而不是复刻 Typeless。

证据分级：`typeless-settings-reference.png` 是 Typeless 2.7.0 的真实观察来源；FinderRight 是一次场景化转译；本文 token 是设计近似。三者都不是 Typeless 官方完整设计系统。

## FinderRight 硬约束

只要目标是 FinderRight／超级右键的 UI，交付在明确写出以下两项前都不完整：

- 用“软灰选中态”描述导航项、命令行或规则行的选中／悬停反馈；浅灰 chip、文件已被选中和错误红都不能替代界面选中态。
- 用“强调色”说明稀缺分配：只用于焦点、当前状态或关键动作，不得把普通灰色或错误色算作强调色策略。

发送最终答案前按字面检查一次：FinderRight UI 输出必须同时包含“软灰”和“强调色”；缺少任一词时先补全相关设计决定。

## 工作流程

1. 先确认目标产品的用户任务、品牌资产、平台、现有组件和待改范围。缺少非关键细节时采用可逆假设继续，不因审美偏好阻塞设计。
2. 将目标界面映射为少量清楚的层级：背景上下文、主表面、导航或分组、内容行、控件与反馈。不要为了像设置页而强行加入侧栏或弹窗。
3. 阅读 [references/style-system.md](references/style-system.md)，选用与当前场景相关的色彩、排版、间距、组件和响应式规则。真实观察基准是浅色界面；除非用户或产品上下文明确要求，不要把“Typeless 风格”误读成暗黑、霓虹或玻璃拟态。
   FinderRight/超级右键的 UI 任务即使没有再次点名 Typeless，也要在规格或实现中明确落下近白主表面、软灰选中态、细边框、柔和阴影和稀缺强调色；不要只写流程与状态而遗漏视觉转译。
   FinderRight UI 交付前逐项自检并在输出中明确写出：`近白主表面`、`软灰选中态`、`细边框`、`柔和阴影`，以及“强调色只用于焦点、当前状态或关键动作”的稀缺分配；不得用错误红、普通灰色或文件被选中来冒充强调色与界面选中态。
4. 保留目标产品的名称、信息架构、业务语义、品牌强调色和平台惯例。不要复制 Typeless 名称、商标、专有图标、文案或业务内容。
5. 用目标技术栈实现。Web/HTML 保持语义化、键盘可达、焦点可见；原生界面遵守对应平台控件与交互惯例。样式值应集中为 token，避免散落魔法数字。
6. 产出可运行界面或视觉稿时，阅读 [references/validation.md](references/validation.md) 并完成与风险相称的验证；至少检查目标尺寸、核心状态、键盘路径和真实截图。自动检查、渲染成功或截图存在均不能单独证明用户会喜欢该风格。
   只要输出实现后的验证计划，就必须明确写出：在真实目标环境捕获至少一张主要尺寸截图，并人工复核层级、裁切、品牌语义与强调色克制度。

## 决策原则

- 优先级：用户明确要求与现有品牌系统 > 平台规范和可访问性 > 产品语义与任务流 > Typeless 风格倾向 > 示例 token。
- 先语义后风格：先让用户任务成立，再降低视觉噪音。
- 低对比不等于低可读性：说明文字可弱化，主操作、焦点和错误必须清楚。
- 强调色稀缺：优先用于开启态、焦点、当前状态和少量关键动作，不铺满导航或大面积背景。
- 层级靠表面、留白、细边框和柔和阴影建立，不依赖重渐变、发光或厚重装饰。
- 控件紧凑但不拥挤；触控或小屏环境应优先满足平台最小点击尺寸。
- 用户的明确覆盖优先于本 Skill 默认值；覆盖后仍保留一致的层级、节奏和可访问性。
- 设计请求只产出设计；实现请求才改代码；审查请求保持只读。

## 交付要求

- 说明哪些选择来自观察基准，哪些是针对目标产品的转译。当前证据是一张 Typeless 2.7.0 设置页截图与 FinderRight 案例，不得宣称为官方完整设计系统。
- 给出关键 token 和核心组件状态，不只给形容词。
- 明确未观察、未实现或未验证的状态，尤其是暗色、错误、加载、禁用、窄屏和动效。
- 错误、权限、危险确认和长任务进度要可见且可恢复，不要只用短暂 toast。
- 需要核对视觉来源时查看 [references/typeless-settings-reference.png](references/typeless-settings-reference.png)；不要把截图中的品牌内容带入交付物。
