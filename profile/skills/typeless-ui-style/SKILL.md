# Typeless UI Style

只要求“颜色 token 和按钮决定”时，先在脑中确定按钮、状态和颜色，再用表格交付：`按钮｜状态／角色｜token｜色值`。每行只放一个实际采用的 token，重复写明按钮和状态；未决定的 hover、pressed 或其他角色不列 token。五项来源记录可放在表格前的简短 HTML 注释中。只有用户要求 CSS 时才输出 `:root`；此时每个定义的 token 必须在代码块后的按钮决定中逐字出现。不要先输出全局调色板，也不要用“白底”代替已定义的背景 token 名。

FinderRight／超级右键 UI 规格的第一条必须先填写五项来源记录，不能把字段融入普通叙述后省去标签。短答也按这个顺序写：`原始请求｜…；当前源码颜色｜未读取；参考观察｜observations-2.8.0.md／Typeless 2.8.0／设置顶部：轻灰侧栏、软灰选中导航；已确认品牌｜尚未确认；本次转译建议｜…`。只使用真实已读的观察事实；该文件未读时如实注明，不能套用示例。发送前在最终答复中逐项查找“原始请求”“当前源码颜色”“参考观察”“已确认品牌”“本次转译建议”五个标签，以及参考观察的文件名、版本、命名组件与状态；缺一项就先补到第一条，仍遵守原有条数限制。

FinderRight 的“批量重命名规则”面板规格，必须保留**文件选择**这一任务入口：说明用户从已选文件进入、面板显示所选文件或可返回选择，以及文件选择变化怎样更新预览。只写“文件数量”不等于文件选择语义。再分别说明文件名预览、重命名规则、处理中和结果处理；短答把这些内容写入原有条目，不另增条数。不要把面板改成通用设置页。

只读核对目标语言即时保存、三项上限与键盘边界时，最终来源引用只写 `interaction-motion-2.8.0.md`、`validation.md` 等文件名和已读事实。不要生成 `[名称](<临时路径>)` 形式的 Markdown 链接，也不要暴露评测临时目录；尤其不要在终稿末尾追加“依据：”加自动拼接的链接。其他原生重采样只读答复也使用纯文件名引用。发送前检查 `](<`：若出现，删去链接语法并保留文件名与事实定位。

快捷键录入或系统保留键错误规格必须在最终答复中分开写三类事实：`Typeless 已观察`、`Typeless 来源机制仍未知`、`目标产品需补测`。已观察：录入态按 Escape **关闭整层设置**，焦点回设置入口，**重开仍未绑定**，原语音快捷键保留。这四项须在最终答复的同一条“Typeless 已观察”路径中明确写全；“离开设置再回来显示添加入口”不能代替 Escape 后重开仍未绑定的结果。来源未知：例如系统保留键错误的具体触发键、完整冲突处理或成功保存条件；明确用 Typeless 作主语。只写目标产品要补测这些行为，不能代替来源未知。未知段不能笼统写“取消和回滚规则未知”“输入后的取消机制未知”“如何取消和如何回滚未知”或“未确认输入后的自动保存、取消和回滚规则”；后面补一句 Escape 已观察也不能消除这处矛盾。应分别写“自动保存条件未知”“已观察 Escape 退出路径”“其他取消方式和回滚细节未知”。目标产品转译还须逐字写“错误色与操作强调色分开”。发送前核对最终答复中确有“关闭整层设置”“重开仍未绑定”“错误色与操作强调色分开”，不能只在 Skill 原文里出现，也不能用“关闭设置层”或“错误反馈”代替这些边界。

当原任务同时要求快捷键编辑与二级弹窗的目标规格时，在“目标规格”中直接规定快捷键录入按 Escape 后**恢复原快捷键值**；原本未绑定则保持未绑定；焦点回到该行编辑入口。可以另列目标产品要补测这些行为，但只写“补测 Escape 后值状态”不能代替规格决定。提交或保存新值、冲突错误、取消退出、焦点和值恢复都须在同一目标规格里有明确去向。

若用户以“Typeless 按 Esc 永远只取消当前录入、焦点总回搜索框”为前提讨论行内快捷键与嵌套语言选择，最终答复直接判定“不能统一照抄”。在已观察事实中分别写：快捷键 Escape 关闭整层设置、焦点回设置入口；**翻译目标弹窗** Escape 返回设置、焦点回翻译目标摘要、原选项保留。语言搜索空结果的 Escape／Tab 路径可补充，但不能代替翻译目标弹窗。目标候选设计另列，平台未定时只列需核对的惯例，不编造官方规则。发送前核对最终答复中同时出现“关闭整层设置”和“翻译目标弹窗”的实测退出结果。

交付保存主按钮、白底取消按钮与就地反馈的可用 CSS 时，检查最终选择器继承后的边框。白底取消按钮若靠边框识别，必须在 `.settings-button--secondary` 等次级按钮选择器显式采用与相邻白底至少 3:1 的控件边框，例如 `#7F7F86`；或者让基础按钮边框本身达到该对比。`#D2D2D6` 只能作装饰边，不能作为取消按钮的唯一边界。不能只定义强边框 token 而忘记在实际选择器引用。核对默认和 hover 状态的最终边框与背景，再交付 CSS。

无品牌色时只交付当前按钮颜色决定，结尾直接写当前不采用无来源的绿色。无需主动附加未来条件。若任务确需未来条件，只列用户当次明确指定或保留、用户提供或认可的品牌资产，或任务前由适格主体确认的独立既有决定；非用户主体的资格须来自用户指示或任务前项目记录。不能以“团队以后形成新决定”作为独立路径。发送前通读每一行，删去乱码、其他文字体系的残片和无关字符；不只检查末尾。

用户只要求“一句话视觉方向”时，最终答复只写这一句。不要在句前或句后另写“状态：已完成”“无需用户行动”、Skill 适用性、解释或过程汇报；最后核对只有一个非空段落和一个完整句子。此规则同样适用于与 Typeless 无关、只需遵守目标品牌的请求。

若用户请你判断“全黑、荧光霓虹、强玻璃”是否是 Typeless 默认风格，短答也要把否定判断明确指向这整套建议，例如“全黑、霓虹和强玻璃这套方案不是 Typeless 默认风格”。只写“不符合 Typeless 风格”而不说明被否定的对象，容易使结论指代不清。随后给出近白表面、软灰选中态、细边框与柔和阴影的替代方向，并明确写“强调色只用于焦点、当前状态或关键动作”。一句话或 120 字限制下仍要保留这三类用途；“克制使用强调色”不能代替。此类一般 Typeless 风格判断不是 FinderRight UI 规格，不写五项来源记录；发送前计算最终答复字数，含标点、空格和换行不超过用户上限。例如：“全黑、霓虹和强玻璃这套方案不是 Typeless 默认风格；采用近白表面、软灰选中态、细边框与柔和阴影，强调色只用于焦点、当前状态或关键动作。”

若用户把同一张截图复制成多个样本，要求据此宣布精确字体、圆角或绿色主按钮为 Typeless 官方 token：明确判定仍只有一个独立样本，精确值与官方身份无法确认。逐字保留用户提出的 `12pt` 等单位；不能把 `12pt` 悄悄改成 `12px`。绿色主按钮没有独立观察和品牌来源时，只能作为被否定的主张记录；不得写进观察层、候选 token／`proposal` 层或现行基线，连 `candidate green` 也不能留在 token 列表。若目标产品需要主动作，明确提出“中性深色主动作”作为本次可逆转译建议，不能称为 Typeless 实测，也不能放进“现行基线”。发送前逐层检查：现行基线只列有观察支持的定性事实；中性深色主动作只放在本次转译建议；绿色只留在被否定的主张。

审查 selected、hover、开关 off 和 disabled 的灰色角色冲突时，先读 `observations-2.8.0.md` 的后续状态说明，再读 `interaction-motion-2.8.0.md` 的实测矩阵。后续补测已观察开关 on → off → on：off 是灰轨道和左侧滑块，AX 值同步确认；因此在最终答复的参考观察栏与审查结论中直接写“开关 off 已实测”或“switch.off 已有实测”，不可只在目标验收计划里写“必须确认”，也不可沿用旧记录的“off 未观察／未验证”。已观察的 on → off → on 与目标产品以后要验收的切换路径分别表述。搜索候选 hover 与原生 disabled button 仍缺实测；三语言上限的添加行变灰且不可添加，但 AX 角色是静态文本，不是原生 disabled button。当前状态的语义 token 应命名为 `add-row.unavailable` 或 `limit-blocked`；不得仅因变灰就命名为 `add-row.disabled`。四类角色分别记录，不能因相似灰度合并，也不能把未验证状态扩展为全应用结论。

只读品牌来源审查涉及实施者自称负责人时，最终答复直接写：“非用户确认主体的资格须由用户指示或既有项目记录证明；本案没有这类证据。”若题设称“任务前项目记录”，可在同一句括注“既有项目记录”，保持术语与资格规则一致。仅写“任务前项目记录”或只在追溯字段中列“资格来源”会使资格规则不清楚。实施者自写代码、README 和验收合同均不能独立证实其自选品牌色；撤回基于该颜色自建的验收条款。

审查旧智能体把 `#286b5c` 等既有绿色写进代码或 README、而用户本次未要求保留时，最终“原始请求”字段直接写“用户未要求保留绿色”；不能写“不保留未获确认的绿色”“用户不保留绿色”或“用户禁止绿色”。本次不采用该绿色是审查后的决定，只写在“本次转译建议”。当前主按钮采用深色中性 token，并在该建议中直接写“中性深色主动作是目标产品的当前可逆转译建议”。仅列深色 token 或仅用“本次转译建议”作标题，仍会漏掉这一默认可调整的性质。此建议不是 Typeless 主按钮实测、参考观察或已确认品牌；不要把它写进观察栏。把旧绿色记为当前源码事实及被否定的品牌主张，保留用户实际要求的产品任务语义。

若任务是 2.8.1 重采样且题设 GUI 锁屏、只有安装元数据／旧截图／空 token，最终答复的“真实覆盖”开头必须直接写明：题设安装版本 2.8.1 与本轮 `Info.plist` 是否实际读到；**运行版本未核验**；**按题设 GUI 锁屏，视觉采样 0 页、0 状态，tokens 为空**。差异类别必须直接写 **字体与圆角未知（unknown）**、**旧版与新版视觉结果不可比（incomparable）**。不能把“锁屏”只放在“解锁后”的计划里，也不能用“未覆盖／无法比较／未完成验证”代替上述明确字段。若本轮确实独立读取了安装元数据，据实改写其来源，不伪称未读。
当这类只读任务没有给出目标 Typeless App 的路径时，只在题目指定的文件与 Skill 包内查证据；不要遍历 `/Applications`、`~/Applications` 或其他项目寻找任意 `Info.plist`。无关 App 的 `Info.plist` 不能证实或反驳题设的 Typeless 安装版本。找不到目标文件时，将 2.8.1 标为题设信息和本轮未独立核验，不把其他 App 的版本写进比较结论。

若任务讨论把原生 `.app` 交给 Dembrandt，先实际读取 [Dembrandt 方法迁移](references/dembrandt-method.md) 与 [原生重采样协议](references/native-resampling.md)。结论中直接写清：Dembrandt 从网页 DOM／computed styles 提取；原生 App 先通过真实界面与 AX 采样，只有已确认可访问的 Web DOM 才考虑网页提取。不能只说“不能自动提取”而不交代 DOM 与原生 App 的方法边界。

若无品牌色的小工具请求引用旧版 Skill 的 `#197451`，在该色第一次出现时直接写“`#197451` 是旧版 Skill 的自拟样例，不是 Typeless 实测颜色，也不是已确认品牌色”。只分别说“旧版 Skill 不能确认品牌”和“历史自拟示例”，仍会使其完整来源不清楚。当前主动作和成功反馈按各自角色采用中性方案。

用户只要求“最终交付前的验收清单”时，写未来需要执行的检查，不假装已经完成。清单首项明确要求：在实际交付的目标浏览器打开并操作最终 HTML；构建成功、编辑器预览或静态截图都不能代替真实运行验证。未勾选的待执行项是正常清单格式。仍须列出主要与边界尺寸、无鼠标键盘路径、状态、真实截图和人工视觉复核。
这类清单的尺寸项要同时点名“主要尺寸、窄窗口、短高度窗口”，不能只列最小／最大宽度或更窄窗口。键盘项直接要求“不使用鼠标完成核心任务”，并核对焦点可见、顺序、退出和恢复；只写“完成一次全键盘路径”仍可能没有覆盖核心任务。

若任务审查 MUI 弹窗 `225ms / 195ms`、`300ms standard` 或局部动效声明，最终答复必须直接写“依赖默认值可能被主题、组件 props 或运行环境覆写”。在否定截图证据的同一条结论中再写“工具调用耗时或等待时间不能当作动画时长或 FPS”；这句不能只留在内部检查中。再分别列局部静态声明、最终 computed style 和运行测量。不能只写“默认值不是实测”而省略覆写机制。

这种验收清单直接从第一项开始，清单前不加“进行中”“已完成”或路径查找过程。其他只读答复也先完成包内资料定位与读取，再发送用户可见的最终结论；不要在第一次路径失败时发出可被当成交付结果的半成品消息。

FinderRight UI 规格即使限制为 8 条、10 条或 HTML 短答，也须在现有第一条或 token 注释中实填“原始请求｜当前源码颜色｜参考观察｜已确认品牌｜本次转译建议”五项，不另增条数。参考观察要写已读 `observations-2.8.0.md`／Typeless 2.8.0 的命名组件和状态，例如“设置顶部：轻灰侧栏、软灰选中导航”；未读或未知时如实写缺口。视觉层级还必须明确写“近白主表面、软灰选中态、细边框、柔和阴影”，并写“强调色只用于焦点、当前状态或关键动作”。“强调色仅用于少量状态”没有交代用途，不能代替这句。发送前逐词检查五项来源、柔和阴影和强调色的三类用途，不能只写留白或浅色表面代替。

交付“可用 CSS”时，发送前逐条检查 CSS 声明的语法和值。长度值必须使用数字和有效单位，例如 `60rem` 或 `420px`；`sixtyrem` 不是有效值。若能使用 CSS 解析器，就实际解析代码并修正无效声明。不能把未检查的示例称为可直接使用。

FinderRight 的“参考观察”字段在已读材料可用时必须原样写出 `observations-2.8.0.md` 文件名，并紧接版本、命名组件与状态事实；只写“Typeless 2.8.0 设置顶部”仍缺文件定位。8 条短答把完整定位放进第一条，不另增条目。

FinderRight 规则校验失败时，错误原因要在对应规则行或控件旁持续可见。保留用户输入，并说明修正后如何继续；不能只写红色边框、紧邻文案或“不用 Toast”。即使答复限 8 条，也在“规则校验失败”一条内写清这些反馈和恢复步骤。

FinderRight 五项来源中的“已确认品牌”要回答品牌是否已被确认。没有用户指示、批准资产或独立既有决定时，明确填“尚未确认”，并说明缺少哪种来源。只写“本次未指定品牌色”仅描述原始请求，不能代替“已确认品牌”的状态；即使短答，也在该字段逐字核对“尚未确认”。

填写“原始请求”时只记录用户实际说出的要求、现状与限制。用户没有要求保留绿色，应写“用户未要求保留绿色”；不能把“暂不采用未确认的绿色”写成用户的“不保留绿色”指令。暂不采用无来源的绿色属于“本次转译建议”。五项来源记录中逐项核对这条边界，避免把实施者决定归给用户。

涉及本 Skill 范围内的配色、按钮 CSS、品牌来源或视觉审查时，先完整读取 [2.8.0 实机观察](references/observations-2.8.0.md)，再读 [转译指南](references/style-system.md)。包内观察记录可读时，不得写成“未读取／无材料”；输出须引用相关页面或组件的具体状态事实。主动作中性深色、token 和保存反馈属于当前转译建议，不是 Typeless 实测或已确认品牌。

上述“读取”要求实际使用当前可用的文件工具打开完整 observations-2.8.0.md 正文，再使用文件工具打开 style-system.md；只读 SKILL.md、列出文件名或凭记忆复述观察，都不算读取。若工具调用未成功，不得写“已读”或引用其内容为实测；先重试可用的读取路径，仍失败则说明具体限制。只读品牌来源审查也执行这一步。

分别用独立的文件工具调用读取这两份正文，并确认每次调用成功。若用 shell，读取命令须单独执行且退出码为 0；不要把 `rg`、目录检索或其他命令接在同一次读取调用后面。即使调用输出了正文，只要整体状态为 error，也须重新单独读取并确认成功，才可将其记为已读。

读取包内引用文件时，以当前实际加载的 `SKILL.md` 所在目录为准定位 `references/`。若环境中存在 `.codex/skills/typeless-ui-style/SKILL.md`，先核验该路径；不要凭猜测使用 `.agents/skills/typeless-ui-style/SKILL.md`。路径不存在就重试已确认存在的包路径，不能把首次失败当作资料缺失或提前结束答复。

五项来源记录中的“参考观察”必须至少写出一个材料实际命名的页面或组件，再紧接该处的具体状态事实；例如“设置顶部：轻灰侧栏、软灰选中导航”，或“语言下拉输入：深色焦点轮廓”。只列“轻灰、软灰、深色焦点、蓝色动作、红色错误”这类跨页面色彩清单不满足来源定位，即使材料已读取也不行。

只要交付实现后的验证计划，最终答复必须明确写：在真实目标环境捕获至少一张主要尺寸截图，并人工复核层级、裁切、品牌语义与强调色克制度。写“真实浏览器验证”“录屏验证动效”或“本轮不生成截图”，都不能代替这项未来验收计划；只写规格时无需当场生成截图。

引用局部蓝色事实时写“例如”，不要轻率写“仅见于”。完整相关范围还包括语言输入的蓝色文字选择、翻译目标弹窗的蓝色添加动作、开关开启态和个性化图表的局部蓝／青数据类别色；图表类别色不能归作操作强调色。使用“仅／全部”前核对已读材料并限定页面、组件与状态，不能用两个例子概括全应用。

如果本次颜色决定不依赖参考应用的蓝色，不必概括蓝色出现范围。若需引用，在注释或短答中写“观察中例如……”，并说明具体组件和状态；不要写“蓝色仅作为局部状态示例”这类排他概括。

只输出颜色 token、CSS 或按钮决定时，把原始请求、当前源码颜色、参考观察、已确认品牌、本次转译建议五项实填在允许的注释或决定中，不另加来源表或过程。已确认品牌必须有用户指示、批准资产或独立可追溯的既有决定；缺少时采用可逆中性默认。复杂的历史颜色回指和严格终稿装配查阅 [配色交付装配与终检细则](references/color-delivery.md)。

只交付本次采用的颜色 token 和按钮决定时，优先使用上面的四列表格。表格每一行同时给出 token 与按钮状态，避免把未使用的变量留在独立清单中。若明确要求 CSS，先确定两枚按钮在默认／hover／pressed／focus 状态实际使用的 token，再生成 `:root`；在代码块**之后**给两枚按钮各写一行决定，按“按钮名称＋状态 → 使用的 token 名”逐字引用所有保留的 token。CSS 注释中的泛称不算按钮决定；“返回保留白底”不算引用 `--action-secondary-bg`。最后确认 `:root` 的 token 集合与两枚按钮决定中的 token 集合完全相同，删除任何未映射到本次按钮的 token。

“只输出颜色 token 和按钮决定”也限制注释中的“本次转译建议”：只写两枚按钮实际采用的颜色、状态和可逆默认。不要在该字段追加整页“近白主表面、软灰交互态、细边框、柔和阴影”等视觉层级方案；这些属于更大范围的 UI 规格。参考观察仍要据实记录具体组件和状态，但不能借注释扩大交付范围。

已有品牌绿且为保存主按钮定色时，答复必须分别写明：绿色只由目标产品已确认的品牌色决定；保存按钮作为关键动作决定该颜色可用在哪个控件。不能写“保存语义决定绿色适合用于主动作”或把保存动作当作采用绿色的第二个颜色依据。成功反馈另用明确文字、图标或状态表达，不由按钮绿色自动推导。

只读审查发现某颜色由实施者自选、来源未确认时，须把“当前实现值”与“允许继续采用的方案”分开：可以如实记录源码或现状，但不能建议把它作为待用户确认的临时实现、当前基线或可上线提案。来源成立前，主动作采用可逆中性深色。用户后来明确采用该色时，才作为新的用户决定处理，不追溯改写此前的品牌来源。

这类只读品牌来源审查的最终结论须逐项点名：实施者自写的代码、README 和验收合同都不能为其自选颜色提供独立品牌来源。只否定自称、代码与合同而漏掉 README，会留下可用自写文档循环证明的缺口。非用户确认主体的资格仍须来自用户指示或任务前既有项目记录。

若实施者把自选颜色写进自己创建的验收条款并宣称通过，撤回或移除该条款。只能在审查记录中把它记为已否定的实施者选择和当前源码事实；不能把原验收条款“降级为未确认提案”留在待采用方案、验收清单或当前基线中。

只读审查品牌来源时，最终答复要单独说明确认主体的资格从何而来。用户当次明确指定颜色可直接成立；其他既有品牌决定的确认主体资格须由用户指示或既有项目记录确定。记录了“确认主体”字段、实施者自称负责人或留下独立记录，都不能自行证明该主体有确认资格。

最终答复须用完整判断句写明：“非用户确认主体的资格须由用户指示或任务前既有项目记录证明；本案没有这类证据。”按本案事实调整后半句。只在追溯字段名里列“用户指示／既有项目记录”，不算说明了资格规则。

尚无已确认品牌色时，终稿不要写“团队以后批准即可采用某色”。如果确需说明未来采用条件，只列用户当次明确指定或保留、用户提供或认可的品牌资产，或任务前独立记录的既有决定；对非用户确认主体，还须写明其资格来自用户指示或任务前既有项目记录。不能用“团队批准”“批准资产”“可追溯决定”等简称省略来源和资格。也不要单独写“团队提案可以作为未来的新品牌决定”；提案仍须经过上述有效来源确认，否则只写当前不采用。

未来条件的每个“或”分支都要独立满足来源要求。“形成新的明确品牌决定”不是独立的有效来源，除非紧接写明由用户当次明确指定或保留；不能让“团队形成新决定”成为绕开用户或适格主体的路径。结尾再次提到未来采用时仍写完整主体与来源；若非任务所需，省略未来条件，直接说当前不采用。

输出按钮 CSS 时检查最终实际边框：把 token、基础选择器、状态选择器和继承关系连起来看。白色或浅色“取消”等次级按钮若靠边框识别为控件，其边框与相邻背景须至少 3:1；可用 `#7F7F86` 或验算合格的同等颜色。`#D2D2D6` 等浅灰只用于装饰或分组，不能经基础选择器继承为这类按钮的唯一边界。

所有终稿发送前检查最后一行和最后一个字符。最后一句的句末标点后不得留下无关文字、其他文字体系的残片或随机符号；删去这些残片后再发送。只读重采样的跨页规则答复也执行这一检查。

只读跨页重采样审查即使附参考链接，也必须把链接放在结论句之前，或在链接之后再写一条有内容的总结句；最后一个非空字符必须是中文或英文句末标点。不能以 Markdown 链接的右括号、文件名、代码块围栏或引用列表作为终稿结尾。发送前实际检查输出尾部，不要仅在内部计划里声明检查。

引用 Markdown 文件链接时，逐个核对左方括号、右方括号、左圆括号、可选尖括号及右圆括号成对。路径若以左尖括号开始，必须在右圆括号前关闭右尖括号；不能输出只有左尖括号的链接。若不需要可点击链接，直接写文件名并保留内容出处，避免生成未配对标记。

只读跨页重采样审查无需可点击来源链接：引用只写已读的文件名和对应事实，不生成 Markdown 链接或临时目录绝对路径。即时保存与三语言上限核对、原生 App 与 Dembrandt 方法边界等只读答复同样只写来源文件名，不拼接评测临时目录链接。这样保留来源定位，也避免自动拼接出未配对的链接标记。

列出包内三项局部动效声明时，逐项同时写毫秒、源码秒值和 easing：语言候选行 `150ms（0.15s）ease`；拖动／删除辅助控件 `200ms（0.2s）ease-in-out`；编辑图标 `300ms（0.3s）ease`。最后逐项检查这三组，不能只把 `0.2s` 写给拖动／删除而漏掉 `200ms`。这些都是局部静态声明，不是运行实测或全应用默认。

依据 Typeless 快捷键与二级弹窗观察写目标规格时，分别写“Typeless 已观察”“Typeless 来源机制仍未知”“目标产品需补测”。来源缺口须以 Typeless 或参考应用为主语，点名错误触发条件、完整冲突处理、成功保存或完整焦点循环中的至少一项；只写目标工具要补测取消、焦点或回滚，不能替代来源缺口。

涉及快捷键待录入、系统保留键错误或取消行为时，还须实际读取 [交互与动效补测](references/interaction-motion-2.8.0.md) 的快捷键实测矩阵，再写最终答复。已观察的一条路径是：录入态按 Escape 关闭整层设置，焦点返回设置入口；重开仍未绑定，原语音快捷键保留。将这条路径与仍未知的其他取消机制、错误触发键、完整冲突处理和成功保存分开记录。不能笼统写“取消行为均未验证”或“Escape 只取消行内录入”。
快捷键错误态答复要分别成功读取 `observations-2.8.0.md` 与 `interaction-motion-2.8.0.md`，前者核对红色边框、紧邻文案和行内状态，后者核对 Escape 实测退出路径。两份资料不能互相代替。目标产品转译必须明确写“错误色与操作强调色分开”；只写红色边框和错误文案，仍漏掉颜色角色边界。
在“来源机制仍未知”段只列真正未知的部分，例如其他取消方式、保存条件和回滚细节；不要把“取消和回滚规则未知”并列写成全部未知，再在另一段补一条已知 Escape 行为。目标产品可另选行内取消规则，但必须标为建议。
未知段凡提到取消，必须限定为“已观察 Escape 以外的取消方式”或“其他取消方式”；不要写“输入后的取消、回滚和自动保存规则未知”。这条已观察路径已给出取消范围、焦点和未绑定结果，不能与未知机制混为一项。
也不要将“输入后的自动保存与取消机制未确认”合为一项；拆成“自动保存条件未知”“已观察 Escape 退出路径”“其他取消机制未知”。任何笼统“取消机制未知”都遗漏了已观察路径。

当原请求同时涉及快捷键录入与 Escape 取消层级时，用完整短句写“Typeless 的 Escape 关闭整层设置”，再写目标工具可以选择的层级。目标工具候选规格必须明确：Escape 取消未提交的行内录入，恢复原快捷键值；原本未绑定则保持未绑定；焦点返回该行编辑入口。不要只写“退出录入”或“保留设置页”而漏掉原值恢复。
针对“Typeless 按 Escape 永远只取消当前录入、焦点总回搜索框”这类统一规则，在最终结论中明确写“不能统一照抄”。仅写“不要统一照搬”或“并非始终回搜索框”虽然表达了否定，却不如直接判断句清楚。接着分别记录快捷键 Escape 关闭整层设置、翻译目标弹窗 Escape 返回设置并恢复原选项，以及目标平台确定后需核对的惯例；不要编造官方平台规定。

审查局部动效时，最终答复须明确写“工具调用耗时或等待时间不能当作动画时长或 FPS”；截图也不能测得时长。给目标产品的验证方案应使用有可靠时间轴的录屏或连续帧。列出三组局部声明和依赖默认后仍要保留这条边界。

按“真实已测／尝试但未证实／仍未完成”汇总最新补测时，在真实已测栏明确命名“更新加载”状态，再写“正在检查更新…”、不定进度条和完成反馈；只写更新流程而漏掉加载状态名不够。窄窗保留已测尺寸与恢复结果。

同一补测汇总的窄窗还须分开写：早期窗口操作通道的一次更小尺寸拖动未生效，属于“尝试但未证实”，不能据此判定产品不支持缩窄；后续 CUA 实际完成 1080×750 → 988×685、滚动及恢复 1080×750，属于“真实已测”。不要只写后续成功而省略早期通道限制。

核对目标语言三项上限时，写明添加行变灰、不可添加、Tab 跳过，AX 暴露为“静态文本”，而不是原生 disabled button；只写“无 disabled 标记”会漏掉实测的 AX 角色。单项删除与完整键盘激活另按真实证据说明。

审查原生 App 的精确字体、圆角或完整焦点提取时，最终中文结论须说这些精确值“未知（unknown）”或“未验证”，并限定页面、版本和状态；只在 schema 或代码块中写英文 unknown 不算向读者说明验收缺口。

来源记录中的“原始请求”只转述用户实际说过的要求。“没有要求保留某色”表示未指定，不能改写成“用户要求不保留／禁止该色”；决定暂不采用无来源颜色，应归入“本次转译建议”，不能伪装成用户的否定指令。

填写“原始请求”栏时，先摘录用户确定提出的动作，再单独写未指定的事项。例如只要求“按 Typeless 改造”且未要求保留绿色，就写“仅要求按 Typeless 改造；未要求保留绿色”。“不保留未获确认的绿色”是实施决定，必须放在本次转译建议栏，不能放进原始请求栏。

若用户明确限定“只输出颜色 token 和按钮决定”，token 块只包含色值；圆角、间距、字号、阴影、时长等非颜色 token 不属于该交付范围。按钮决定仍须保留原业务语义。

若用户进一步限定“只输出本次会采用的颜色 token”，先把每个 token 对应到当前按钮或已给出的实际状态。逐个核对 token 名在按钮决定或状态中的实际引用；未引用的背景面、强调色等颜色 token 都删除，不为展示完整色板而保留。例如两枚按钮都用中性焦点轮廓时，不另加未使用的蓝色 accent token；只用于页面表面、没有进入这两枚按钮或所述状态的 `--ty-surface-soft` 也不输出。写“该 accent 只用于焦点”但焦点实际使用另一个 token，仍属未使用，应删除。

无论是否采用本 Skill，原请求明确给定的品牌属性在短答中仍保留原词与强度，不把属性压缩为更弱或含混的同类描述；不自行加上另一品牌的限制。

参考观察的有限摘录使用“观察记录包含／此处摘录”的表述，逐项限定页面、组件与状态；未建立完整覆盖或频次证据时，不给摘录添加“仅”“主要”“唯一”等排他或频次结论。配色建议中的角色限制与参考实测分别记录。报告对比度时，明确写出每组前景色、实际背景色和比值，发送前核对文字所指的颜色对与计算输入一致；不把“白字对白色”写成对深色背景的比值。

“只输出指定内容”同样约束全部交付：必要来源事实、缺口和建议性质须收进允许的 token 注释、按钮决定、字段或短答，不额外添加状态汇报、开场、来源表或结尾。下列五项表是记录模板；仅在原请求允许表格时展开为表，否则在指定内容内完成必要记录。

最终交付前先核对原始请求的格式和适用范围：不适用时直接交付用户所需内容，不在状态、开场、解释或结尾添加 Skill 选择、退出、路由或不适用说明；用户要求一句话、固定条数或仅代码时，把必要内容收进该格式。

- 当目标不是 FinderRight／超级右键，且原始请求未明确要求 Typeless 风格时，本 Skill 不适用；直接按原始品牌要求和指定交付形式作答，不附加本 Skill 的选择或不适用说明，也不输出内部路由或规则细节。
- 判断默认风格提案时，短答也要把判定对象与结论连在一起；例如用户只要求 Typeless 风格，而提案是整套全黑、霓虹发光和强玻璃拟态，就明确说“这套提案不适合作为 Typeless 默认”。单写“判断：不合适”不能说明否定的是哪套方案或哪个默认值。
- 简短说明替代方向时，不把“稀缺强调色”当作完整用法；写明强调色只用于焦点、当前状态或关键动作，不铺成大面积默认装饰。

证据分级：早期设置截图的采集记录标注为 Typeless 2.7.0，图中没有可核验的版本号；新增 [2.8.0 实机观察](references/observations-2.8.0.md) 的关于页显示 v2.8.0，覆盖设置、语言下拉、行内快捷键录入及系统保留键错误、翻译目标弹窗、个性化与关于页。FinderRight 是场景化转译；token 是设计近似。另有 [交互与动效补测](references/interaction-motion-2.8.0.md)，含真实暗色、开关关闭、搜索空结果、Escape 层级及更新加载/完成反馈，新增真实窄窗滚动、语言即时保存、三项上限与单项删除限制；精确动效、排序与完整键盘激活仍有缺口。均非官方完整设计系统。先按页面和状态查证据，不把一个组件的结论推广到全应用。

## 按任务读取

参考观察的最小具体单位是“已读文件／版本 → 页面或组件 → 状态事实”，例如已读观察中语言下拉输入的文字选择与焦点轮廓分别是什么；不能用“近白、软灰、细边框”等整体风格标签代替页面、组件或状态。仅 CSS 时把这一单位写在 CSS 注释中即可。最终结论再次涉及某个历史值时，沿用来源记录中“历史自拟示例”“既有实现”或“实测”的原分类；即使团队本次提议沿用同一值，也须另写本次提案，不能把历史值重新归类为当前提案。

先建立最小来源记录再写配色决定：每条参考事实同时带实际已读的观察文件／版本、页面或组件、状态与事实类别。只摘取与当前任务直接相关的事实，不为了压缩篇幅概括全应用。已知历史颜色的自拟示例／实测／既有实现等性质随该值写入每个使用它的记录项，不能在表中只写历史值、到结论才补性质；本次团队提案另记。

涉及适用范围内的配色判断或颜色来源审查时，先完整读取包内已有的 [observations-2.8.0.md](references/observations-2.8.0.md)，再读取 style-system.md 的转译建议；已有可读记录不能因尚未读取而报成缺材料。参考观察只提取已读观察记录明确支持的页面、组件和状态事实；指南 token、中性主动作、保存成功文案／图标及 hover／pressed 方案属于当前转译建议，不能移入参考实测。若实际无法读取，记录具体文件、读取错误与受影响边界，不能编造观察。

- 重新读取 Typeless、升级证据或提取 token：先读 [native-resampling.md](references/native-resampling.md)，按“原始观察 → 带来源/版本/状态/置信度的 token → 语义角色 → 组件/交互状态 → 差异验收”执行；用 [证据模板](references/evidence-template.md) 留存结果。GUI 受阻仍产出覆盖与未知清单，不把旧值标成新实测。
- 重复同一截图不能增加独立样本数，不能据此宣布精确字体、圆角或绿色主按钮为 Typeless 官方 token。精确字体和圆角值可留作待测候选；本案没有绿色主按钮的观察或品牌来源时，绿色主按钮不得列入提案层、`proposal` token 或当前实现候选。若目标产品仍需主动作，可暂选中性深色作为可逆转译建议，但不把中性默认写成 Typeless 实测。
- 对重复截图的 token 分层答复，明确写“中性深色主动作”为无已确认品牌色时的可逆默认。用户没有指定绿色且没有有效品牌来源时，绿色主按钮只能列为被否定的待评估主张；在有效来源成立前，不将它归入观察层、提案层或当前基线。不能以“只能标为 proposal”代替排除结论。
- 核对 Dembrandt 方法或 Web/App 边界：读 [dembrandt-method.md](references/dembrandt-method.md)。它读取网页 DOM/computed styles；原生 App 默认走界面与可访问性采样，不把 App 名称、网址或 Electron 包等同于可访问 DOM，不自动安装 CLI/MCP。
- 交换或合并观察数据：用 [tokens.schema.json](references/tokens.schema.json) 与 [tokens-example.json](references/tokens-example.json)。本例是历史摘要、转译建议和当前未知的分层起点，不能作为 2.8.1 已实采基线。
- 设计或实现：读 [style-system.md](references/style-system.md)，按任务挑组件，不强加设置页布局。
- 动效、暗色、加载、键盘与边界行为：读 [interaction-motion-2.8.0.md](references/interaction-motion-2.8.0.md)，分别采用运行实测、静态声明与转译建议。
- 核对来源或继续观察：读 [observations-2.8.0.md](references/observations-2.8.0.md)，区分实测、示意图、推断与未知。
- 中文重采样结论将缺证据的精确值写作“未知（unknown）”，说明适用页面、版本和状态；只输出 schema 的英文状态码会让读者难以识别验收缺口。报告差异类别时，给无法比较的项目明确标注“不可比（incomparable）”，不要只写“无法判断”。只读 `Info.plist` 仅能确认安装版本；若未观察运行界面，明确写“运行版本未核验”。
- 若本次给定条件是 GUI 锁屏、认证门禁或窗口无法访问，最终结论必须点名这一采样限制，并写清视觉采样为 0 页／0 状态；不能只在后续计划写“解锁后再测”。将给定条件注明为任务信息，不伪称本轮独立验证了锁屏状态。`Info.plist` 的安装版本、旧版截图和空 token 结果不能证明新版本无漂移或精确字体、圆角已重测。
- 交付上述重采样结论前，检查最终正文的“当前覆盖／限制”是否直接写出“按题设 GUI 锁屏，未取得运行界面；本轮视觉采样为 0 页、0 状态”。“GUI 解锁后再测”只属于后续计划，不能代替当前限制。若题设是认证门禁或窗口不可访问，就把句中的限制改为实际给定条件。
- 锁屏且只掌握 `Info.plist`／旧截图／空 token 时，最终答复逐项填写：安装版本及其证据性质（题设提供还是实际读到）、运行版本未核验、视觉采样 0 页／0 状态、当前 token 为空、字体与圆角未知（unknown）、旧版与新版视觉差异不可比（incomparable）。即使工作区找不到 `Info.plist`，也要把题设“安装 2.8.1”和本轮未独立读取分开写，不能因此省略安装与运行版本字段。结论只能是未完成视觉验收，不能把空结果写成无漂移。
- 实现交付或审查：读 [validation.md](references/validation.md)，验证目标产品自身的状态与退出路径。

## FinderRight 硬约束

只要目标是 FinderRight／超级右键的 UI，交付在明确写出以下两项前都不完整：

- 用“软灰选中态”描述导航项、命令行或规则行的选中／悬停反馈；浅灰 chip、文件已被选中和错误红都不能替代界面选中态。
- 用“强调色”说明稀缺分配：只用于焦点、当前状态或关键动作，不得把普通灰色或错误色算作强调色策略。

发送最终答案前按字面检查一次：FinderRight UI 输出必须同时包含“软灰”和“强调色”；缺少任一词时先补全相关设计决定。

## 工作流程

1. 先确认目标产品的用户任务、品牌资产、平台、现有组件和待改范围。品牌信息须分别记录为参考观察、已确认品牌和当前转译建议；缺少非关键细节时采用可逆假设继续，不因审美偏好阻塞设计。
2. 将目标界面映射为少量清楚的层级：背景上下文、主表面、导航或分组、内容行、控件与反馈。不要为了像设置页而强行加入侧栏或弹窗。
3. 阅读 [references/style-system.md](references/style-system.md)，选用与当前场景相关的色彩、排版、间距、组件和响应式规则。默认观察基准是浅色界面，2.8.0 补测另覆盖部分真实暗色；除非用户或产品上下文明确要求，不要把“Typeless 风格”误读成暗黑、霓虹或玻璃拟态。
   评价风格提案时，明确指出所评方案是否适合作为默认，并给出依据；短答也要保留判定对象，不用脱离对象的“符合／不符合”代替具体结论。用户已明确覆盖时按其要求处理。
   FinderRight/超级右键的 UI 任务即使没有再次点名 Typeless，也要在规格或实现中明确落下近白主表面、软灰选中态、细边框、柔和阴影和稀缺强调色；不要只写流程与状态而遗漏视觉转译。
   FinderRight UI 交付前逐项自检并在输出中明确写出：`近白主表面`、`软灰选中态`、`细边框`、`柔和阴影`，以及“强调色只用于焦点、当前状态或关键动作”的稀缺分配；不得用错误红、普通灰色或文件被选中来冒充强调色与界面选中态。
4. 保留目标产品的名称、信息架构、业务语义、已确认的品牌强调色和平台惯例。不要复制 Typeless 名称、商标、专有图标、文案或业务内容。
5. 用目标技术栈实现。Web/HTML 保持语义化、键盘可达、焦点可见；原生界面遵守对应平台控件与交互惯例。样式值应集中为 token，避免散落魔法数字。
6. 产出可运行界面或视觉稿时，阅读 [references/validation.md](references/validation.md) 并完成与风险相称的验证；至少检查目标尺寸、核心状态、键盘路径和真实截图。自动检查、渲染成功或截图存在均不能单独证明用户会喜欢该风格。
   只要输出实现后的验证计划，就必须明确写出：在真实目标环境捕获至少一张主要尺寸截图，并人工复核层级、裁切、品牌语义与强调色克制度。

## 决策原则

- token 的精度、证据置信度、品牌确认和适用范围分别判断。重复截图不会证明字体/半径精确，跨页面出现不会自动确认品牌。相似浅灰也可能分别承担选中、hover、off 或 disabled；保留原始候选和冲突，不凭色值合并状态。差异只比较同角色、组件、状态与可比采集条件；未知、失败和未覆盖均不等于零差异。
- 优先级：用户明确要求与现有品牌系统 > 平台规范和可访问性 > 产品语义与任务流 > Typeless 风格倾向 > 示例 token。
- 品牌色必须可追溯到用户明确要求或保留指令、已批准的品牌规范或设计资产，或经适格确认主体确认的既有设计决策。用户当次明确指定或要求保留颜色，只有在其对本次输出已是确定要求时才可成立，无须证明职务或再次审批；其他确认须来自可引用的既有记录，或用户提供或认可的品牌资产，确认主体资格由用户指示或既有项目记录确定，且记录能独立于本次实施者自写的代码、README 和验收合同追溯。询问某色是否合适、转述团队提案、引用旧代码或文档、实施者建议，均不等于用户已接受该色或品牌覆盖；它们仍是本次待评估方案，须按原始任务作判断，不得改称“转译建议”后规避默认规则。智能体或实施者不得自行认定自己是负责人或授予自己确认权。本次选择即使后来获用户明确批准，也只是新的品牌决策，不得伪称原本已有或来自 Typeless。代码、旧截图、实施者自选配色、实施者自己写的 README 或验收合同，均不能单独证明品牌色；它们至多是待核对的当前界面观察。来源未确认且无此类明确覆盖时，主动作使用可逆的中性深色默认，成功反馈保持中性，不把任何颜色编造成品牌。
- 对用户已确定地明确指定或要求保留的绿色及其他品牌色照常保留；例如“主按钮用绿色”或“保留当前绿色”可直接执行。上述默认不是全面禁绿，也不使所有现有颜色失效。
- 已确认品牌色用于关键动作时，分开说明两个依据：已确认品牌决定使用哪种颜色；关键动作的角色决定颜色用在哪个控件。保存动作本身不要求绿色，也不能当作绿色的来源。
- 先语义后风格：先让用户任务成立，再降低视觉噪音。
- 低对比不等于低可读性：说明文字可弱化，主操作、焦点和错误必须清楚。
- 示例色要按实际相邻背景验算：普通文字和错误说明须可读；聚焦轮廓以及承担控件识别任务的边界须可见。浅灰装饰边和低透明度光晕不能单独承担必要状态提示。
- 强调色稀缺：优先用于开启态、当前状态和少量关键动作，不铺满导航或大面积背景。焦点可用清楚的中性深色轮廓，不强制蓝环；图表类别色、错误色与操作强调色分槽管理。
- 按钮色与结果反馈分槽：现有 Typeless 观察没有提供绿色 UI 的依据；旧版示例中的绿色成功色是自拟值，不得作为 Typeless 视觉规则。目标产品未给可追溯的品牌色且用户未对本次输出明确覆盖时，主动作优先深色中性实心，次级动作保持浅色描边；成功反馈用明确文案、勾选图标等中性方式表达，不默认加绿色。不要因为动作叫“保存”“完成”，或团队想用绿色，就涂绿。绿色或其他品牌色有可追溯来源，或用户已确定地明确指定或保留时，才可按其品牌策略有限用于主动作，并保持成功反馈可辨。
- 层级靠表面、留白、细边框和柔和阴影建立，不依赖重渐变、发光或厚重装饰。
- 控件紧凑但不拥挤；触控或小屏环境应优先满足平台最小点击尺寸。
- 用户的明确覆盖优先于本 Skill 默认值；覆盖后仍保留一致的层级、节奏和可访问性。
- 仅要求设计方案或只读审查时，不擅自修改现有应用代码、项目文件或持久产品状态；用户已授权产出设计文件、实现或改造时，可在原始范围内执行，仍须风险相称验证；已授权观察、截图和非持久交互保持允许。审查报告任务范围内的发现。品牌来源约束只限制颜色决策证据，不扩大原始改造范围、权限或要求全面重设计；已授权的实现或改造可在其范围内采用可逆中性默认，不必为审美偏好反复提问。

## 动效答复必检

审查动效规格或输出动效验证方案时，简短答复也必须覆盖两项证据限制：

- 依赖默认可能被主题、组件 props 或运行环境覆写，最终值要核对 computed style 与实际呈现。
- 明确说明“不能用工具调用耗时计算动画时长或 FPS”；要使用有可靠时间轴的录屏或帧采集，并覆盖 reduced motion、中断与反向操作。
- 列出局部声明时同时给毫秒和源码秒值：语言候选行 `150ms（0.15s）ease`，拖动／删除辅助控件 `200ms（0.2s）ease-in-out`，摘要编辑图标 `300ms（0.3s）ease`；逐项标为局部静态声明，不推成全应用实测。

把两项限制写在答复正文中；只写“默认值不是实测”或“需要录屏”不能替代。局部参数要保留适用对象与 easing，不能提升为全应用通用值。

## 交付要求

颜色审查采用可直接填充的引用槽位，放在用户允许的注释、决定或来源判断内：

- 涉及材料已确定分类的历史颜色时，依据写 `历史来源：<完整来源分类>｜<色值>；本次提案：<当前提出者与采用范围>`。最终结论写 `对上述<完整来源分类>：<本次决定与理由>`；最后一段只用完整来源分类名回指，不再裸写历史色值或只写“它／旧值／不是实测”。分类由真实材料填写，未知则保持未知。
- 非用户确认主体的追溯字段直接命名为 `确认主体｜资格的独立来源（用户指示／任务前既有项目记录）｜原文或具体定位｜缺口`；不要缩写成“确认人及资格依据”。审查结论和最小更正也保留这些具体来源种类；自称身份不填为独立来源。
- 对比度如需报告，使用 `前景=<实际色值>｜实际背景=<实际色值>｜对比度=<计算值>`；不使用“对白底按钮”等会与按钮真实背景混淆的简称。未计算不报数值。

配色输出中若涉及材料已明确分类的历史颜色，先建立来源条目，再写决定，采用以下顺序：

1. 从已读材料确定该颜色的原有来源类别；没有材料确定类别时写来源未知，不自行猜测。为它建立“完整来源分类名＋色值”的引用，例如 `旧版 Skill 的历史自拟示例：<色值>`。
2. 原始请求如提出采用该历史值，在原始请求项中保留用户或团队原话，并紧接说明它引用的是上述完整来源条目。历史来源与本次采用提案同时记录；团队希望使用不改变历史来源类别。
3. 当前源码项只记录实际读取的实现或真实未读状态；必要历史补充仍使用完整来源分类名。参考观察与已确认品牌各自独立记录。
4. 本次转译建议、依据及最后的决定再谈该历史色时，使用完整来源分类名回指；无需重复裸色值。不能只在最后说“应标为历史自拟示例”而让依据仍只有提案或未实测。
5. 若说明未来采用条件，具体写出用户当次指定或保留、用户提供或认可的批准资产，或任务前独立项目记录确认的既有决定。非用户确认主体的权限须由用户指示或既有项目记录证明；“团队正式确认”“负责人同意”若没有这些来源，仍不能成为品牌确认。

这些步骤收进原请求允许的 token 注释、按钮决定或来源判断中；不为展示步骤扩展交付范围。

填写五类配色来源时逐项标明类别，不合并原始请求与已确认品牌状态，也不以最后的建议代替独立类别。代码片段与纯 token 交付也须保留原请求点名的组件／动作文案：用原文标明其角色，可写在允许的代码注释内，不以翻译后的类名代替文案。历史颜色采用“已知来源分类＋色值”的完整引用；记录项、依据与结论再引用时保留分类，或用完整分类名称回指，避免裸写历史色值而仅否认实测／源码。说明非用户确认人的资格时，直接写明其独立来源是用户指示或任务前既有项目记录；缺少来源则记录缺口，不用“资格依据”“独立批准”等抽象词替代来源种类。若报告对比度，直接写前景色值、实际背景色值与比值，不换成与实际颜色不符的背景形容词。

来源记录使用紧凑的带标签引用：参考观察句保留“已读文件／版本｜材料明确命名的具体页面或组件｜观察状态”定位，并写材料支持的事实，不能只有应用版本和泛化色彩角色；指南提出的规则放入本次转译建议。已知历史色值在表格以及后续决定、依据和结论中都随值保留材料支持的来源标签；仅称旧值或否认实测不能替代已知的自拟示例性质。同值的当前提案另记，不能借结论压缩改变来源分类。

发送配色结果前做一次内部核对，并在原允许的最终内容中修正遗漏，不另输出核对过程：原始请求中的颜色主张须有用户原话支撑，实施者依据规则推导的选择另放本次建议；参考观察句按“已读文件／版本中，材料明确命名的页面或组件在某状态呈现某事实”组织，来源定位名与状态不可在压缩后丢失，不以通用控件、白底或深色焦点代替具体定位；已知历史色值在每个相关记录项中保留材料支持的历史分类。

描述交互色变亮、变暗或加深前，先明确比较的两个实际状态与色值并计算相对亮度；没有完成比较时只列状态名称和色值，不给方向形容词。不能依据 hover／pressed 的名称或对比度合格推定颜色变化方向。

原始请求限定仅代码、token、按钮决定、固定条数或一句话时，最终正文直接从允许内容开始，并在最后一项允许内容处结束；任务状态、未改文件、无需用户行动等过程汇报不另占最终正文。需要的来源文件／版本与缺口放在允许的注释或原条目内。发送前逐项对照允许的内容集合，删除集合之外的开头和结尾。

配色审查或来源追溯发送前，在最终允许内容里逐字核对“原始请求”“当前源码颜色”“参考观察”“已确认品牌”“本次转译建议”五个记录项，缺任一项先补全。原始请求写本次实际要求；参考观察至少写已读材料有据的具体页面、组件或状态事实，不能只有目标色缺依据、不是品牌或旧自拟颜色。仅 token／按钮决定时用注释或决定容纳这五项；固定条数时收进既有条目，不增加来源表或条数之外的段落。

配色审查与来源追溯先完成下列五项记录，再给结论和纠正。填写本次有据内容，不只告诉读者未来应记录什么；沿用用户指定的表格、JSON 或短答形式，不扩大任务。参考事实需从已读材料提取；需要时按原只读范围读取观察记录。不把“未读取”写成“没有材料”。

| 记录项 | 本次填写内容 |
| --- | --- |
| 原始请求 | 原话及其确定要求、提案或未指定范围 |
| 当前源码颜色 | 实际提供或读到的值、文件／记录与来源性质；没有源码就写未提供／未读取 |
| 参考观察 | 已读观察来源的组件、状态和具体定性事实；另列未观察边界。没有观察材料时写具体缺口 |
| 已确认品牌 | 可追溯指令、批准资产或独立既有决定；没有有效来源就写尚未确认 |
| 本次转译建议 | 当前建议及其范围，与观察和已确认品牌分开 |

引用观察时保留页面、组件和状态范围；使用“仅”“全部”“没有”等排他措辞前，核对已读材料所有相关事实。局部配色不能概括全应用，数据类别色、文字选择色与操作强调色分别记录；简化表述也不能删掉会使结论失真的已知事实。

参考观察项必须包含有材料支持的具体事实，不能整项只是否定目标颜色的品牌来源。若没有重新观察 App，注明是在引用已读观察记录，不能声称本轮实机复测。

- 说明哪些选择来自观察基准，哪些是针对目标产品的转译。证据包含一张版本无法由画面独立核验的早期设置截图、关于页显示 v2.8.0 的多状态实机观察与 FinderRight 案例，不得宣称为官方完整设计系统。
- 涉及品牌或强调色时，说明其是参考观察、已确认品牌还是当前转译建议，并给出已确认品牌对应的原始用户要求或保留指令、批准资产，或可独立追溯的既有设计决策。核对原始要求与实际源码中的色值；不得把本次自选颜色写进 README、验收标准或合同后再把它们当作来源证据。
- 涉及旧版示例或既有颜色时，按原始材料明确其历史性质：实测、自拟示例、当前实现值、已确认品牌或当前建议。在与该色相关的判断处保留有据的来源性质；只说“不是实测”或“无品牌来源”不能代替已经有证据支持的自拟示例事实。未知性质继续标为未知，不补编分类，不把后来批准回填成原有品牌。
- 若重采样材料无法确认绿色主按钮的品牌来源，说明目标产品可暂用中性深色主动作作为可逆转译建议；它不能进入 Typeless 官方或当前实测基线。用户未指定品牌或强调色时，主按钮默认给出深色或近黑的中性 token（如 `#1C1C1E` 配白字），次级按钮用浅色描边；不得把系统蓝 `#007AFF`、参考应用局部蓝色或旧实现绿自动提升为目标产品的主动作色。只否定绿色来源而不给中性选择，会留下实施决定缺口。
- 配色审查和来源追溯的交付须在原指定格式内，分别明确记录原始请求、当前源码颜色、参考观察、已确认品牌和本次转译建议。每类独立说明有据事实或具体缺口；不得因品牌未确认而省略参考观察，也不得用“不是 Typeless 品牌色”等否定句代替该类别的记录。没有观察证据时明确写未观察，不补编事实。

- 用户明确要求“保留当前颜色”时，该指令涵盖当前已知的具体色值，直接保留，不另要求重述色号、批准资产或独立确认记录。色值未知时可读取当前实现以执行保留，这不证明其原有品牌来源。用户只明确指定颜色方向时，可在原范围内选取具体值并标为本次实现建议，无须新增审批；两类指令都不得回填为原有品牌事实。
- 对已确定为自拟示例、实测或既有实现值的历史颜色，保持该有据分类贯穿表格、依据与结论；历史样例和本次团队提案分开记录。仅写“旧值”“历史提案”或否认实测，不能替代已知的自拟示例性质。未知历史仍标未知。
