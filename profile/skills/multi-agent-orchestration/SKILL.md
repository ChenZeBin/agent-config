# 多智能体编排

遵守全局 AGENTS.md 的常驻启动核与安全核。仅由主智能体使用本 Skill；子智能体直接完成获派任务，不递归派发。

## 派发判断与数量

- 对非简单任务，主智能体先识别独立分支。通常派发一到两个；只有存在三个低耦合、可独立验收的分支时才派发第三个。
- 研究、代码库探索、测试定位、方案设计、审查、验收，以及写入范围互不重叠的实现，优先派发。
- 主智能体保留整合依赖最强、最需要全局上下文或最终判断的关键路径，不重复执行已派发工作。

## 角色路由

| 角色 | 适用任务 | 边界 |
| --- | --- | --- |
| `explorer` | 只读探索本地代码库或互联网资料，定位文件与执行路径、核对文档并收集可验证证据 | 不修改、不实现 |
| `worker` | 边界明确的代码实现、缺陷修复和针对性验证 | 仅修改明确分配的范围 |
| `acceptance_tester` | 按需求和验收标准执行功能、UI 或端到端验收，操作真实流程并输出可复现证据 | 不负责修复 |
| `strategist` | 为复杂技术或非技术问题提供架构、产品、流程、选型、优先级、资源、成本和风险方面的综合决策建议 | 不实现，不替用户作最终授权 |
| `challenger` | 只读对抗式审查代码或方案，寻找可复现缺陷、错误假设、遗漏、反例和高代价风险 | 不负责实现 |
| `default` | 不属于以上专门角色且边界明确的通用任务 | 专门角色适用时不得使用 |

- 按当前主要交付物选择角色，不要求固定流水线。
- `challenger` 可在高风险方案实施前、代码合入前或发布前介入。
- 主要交付物超出原角色职责时，应结束原任务并重新路由；角色职责内的必要辅助步骤不算越权。

## 派发契约

- 每份派发提示词必须使用最小完备上下文，明确角色及选择理由、目标与范围、读写边界、约束、交付物，以及核验证据或验收标准；仅在影响边界时补充非目标。
- 任务名称应反映具体交付物，不得用模糊名称代替角色和范围判断。
- 优先使用 `fork_turns="none"`；提示词必须自包含。只有关键上下文无法无损压缩时，才继承最少量的近期对话。
- 子智能体应返回可核验依据，例如文件与行号、来源链接、测试命令与结果、复现步骤、截图或风险清单。

## 执行中增量派发

- 执行中发现新的独立分支时可增量派发。

## 证据核验与汇总

- 主智能体负责核对子智能体证据、解决结果冲突并执行必要的最小独立验证；验证不等于重复完成整个分支。
- 收集必要结果后，由主智能体统一汇总完成情况、验证结果和剩余风险。
